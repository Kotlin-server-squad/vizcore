# Part 9 · Learn and story mode — Plan

**Spec:** [2026-11-05 session dock](../specs/2026-11-05-session-dock-design.md), S-9 and S-13 (with S-2, S-5, S-6,
S-11) and its "Story anchors" section.
**Branch:** `feat/part9-story`, worktree `../vizcore-part9`, ports 13901 (UI) / 18901 (API).
**Goal:** a learner who starts a Basics demo reads its guide as chapters in the Learn tab, one at a time. Each
chapter waits for its moment in the run; Reveal moves the whole page (tree, Inspector, slider) to that moment. A
finished demo can be run again in a new session. A backend test proves every chapter's moment is the one its guide
describes.

## What is on main today (the starting point)

- A Gallery or "New demo" start creates a session named `scenario-<name>` and opens it with `?scenarioId=<id>` in the
  address (`use-start-demo.ts:49`). The session API knows nothing of the demo. The page's header offers **Run Scenario**
  (starts the demo in this session), disabled "Scenario Running/Finished/Failed" afterwards
  (`RunScenarioButton.tsx`, which replaced `ScenarioControls`), and "⋯ → Reset session" (delete, then a fresh session).
- The guides ("How it works") are TypeScript (`content/gallery/basics.ts` etc.: `steps: {title, text}[]`).
  `will-see.json` is JSON so that `GuideLabelsTest` can read it.
- Part 8: replay is client-side over a frozen snapshot (`useWorkspaceReplay`); every part shows the replay cursor's
  moment; `enterReplay(snapshot?)` always seeks to the end.
- The Learn tab (`LearnPanel.tsx`) holds the legend and the explanation, marked "Explanation, not recorded data".
- The sessions table already has an unused `scenario varchar(256)` column (V1 schema).

## Decisions

| # | Decision |
|---|---|
| P-1 | **`demoId` on the session.** `POST /api/sessions?name=…&demoId=<catalog id>` records it at creation. An id not in `demoCatalog` → 400 `{"error":"Unknown demo"}` (nothing created). `GET /api/sessions/{id}` (and the share payload, which uses the same `snapshotResponseOf`) returns `demoId` (null when none). Storage follows `ChecksResults`: a new `SessionDemos` object, the row's `scenario` column in database mode, a map in memory mode, forgotten on session close (the `addOnSessionClosed` hook in `Routing.kt`). No core (`coroutine-viz-core`) change. OpenAPI updated. |
| P-2 | **The page's demo is `scenarioId ?? session.demoId`.** The address still wins (old links, sessions created before this part). Everything that is about *which demo* (Run again, Reset, story) uses it; what is about *how the page was opened* (auto-live, the opening tab) stays on the address, as today. So a demo session opened from the sessions list now also offers Run again and its story. Every start passes `demoId` (Gallery, How it works, New demo dialog, Reset, Run again). |
| P-3 | **Run again.** In the header, in place of the disabled button: before the run (`notStarted`) the button stays **Run Scenario** (it starts this session's run, as today); once the run has started (running, finished or failed) it is **Run again**, enabled. Run again: create `scenario-<name>` with the same `demoId` (name = `scenarioName` from the address, else the name in the session id via `sessionDisplayName`), then open it with `?scenarioId=&scenarioName=&run=true`; **the new page starts the run** once its session has loaded and its stream is on (a small `use-auto-run.ts`: once, only while the outcome is `notStarted`, and it drops `run` from the address first, so a reload never starts a second run). Starting it from the new page matters because some demo routes answer only when the demo has finished (`ScenarioRunnerRoutes.kt:145`): started from the old page, the learner would open a finished run. The old session is not touched (no delete, no request to it). A failed create shows in the old page's header error line ("Could not run it again: …") and nothing navigates; a failed start shows in the new page's error line, whose Run Scenario button can try again. Run again while the run is still going is allowed: the old run keeps running in its own session. Reset session is unchanged (it now also passes `demoId`). Not offered in the shared view (mutation). |
| P-4 | **Story anchors live in `content/gallery/story-anchors.json`**, keyed by demo id: an array with **one entry per guide step, in step order** (the TypeScript guide keeps the text; a vitest checks the lengths agree). An entry may be `{}` or hold: `anchor: {event, coroutine, occurrence}` (event = one of the eight coroutine lifecycle events by their wire name: `CoroutineCreated`, `CoroutineStarted`, `CoroutineSuspended`, `CoroutineResumed`, `CoroutineBodyCompleted`, `CoroutineCompleted`, `CoroutineCancelled`, `CoroutineFailed`; coroutine = its label; occurrence ≥ 1, counted per coroutine); `expect: {label: state}` (optional, needs an anchor); `prediction: {question, answers (2–3), correct (index)}` (optional). JSON so the backend test reads the same file (declared as a Gradle test input, like `will-see.json`). |
| P-5 | **The anchor test** (`StoryAnchorsTest`, backend) runs each demo in `story-anchors.json` and, for every anchor: the label names exactly one coroutine; its nth event of that kind exists; the tree **after applying every event up to and including the anchor** (the same state mapping as the page's `projectCoroutines`) has each expected state; anchors are in step order **by event order** (each anchor is the same event as the one before or comes after it), and a later anchor is certain to come after the earlier one in a real run too: the same coroutine, or at least 0.25 scripted seconds later. A chapter may have no anchor. Six Basics run on **virtual time** (`runOnVirtualTime`; their functions gain the `context` parameter the Sync demos already have, default `EmptyCoroutineContext`, no behaviour change); **Dispatcher** uses real `Dispatchers.IO/Default` and runs on real time at scale 0.5 (about 6 s). An unknown demo id in the JSON fails the test with "add it to StoryAnchorsTest". |
| P-6 | **Expected states must be true in a real run, not only in the test's run.** On virtual time, two coroutines that wake at the same scripted instant run in one fixed order; in a real run their order is free. So an expected state counts only if it is **certain** at the anchor: (a) it belongs to the anchor's own coroutine (set by the anchor event itself); or (b) the anchor is a terminal event and the state is a terminal state of one of its descendants (vizcore emits a parent's terminal event only after all its children's, `VizScope.kt:215`); or (c) it is **stable**: that coroutine has no transition within 0.25 scripted seconds before or after the anchor. On virtual time, an event sent from a thread other than the test's (vizcore's deferred terminal events run on the session scope, `VizScope.kt:233`) has no reliable virtual time: `VirtualDemoRun` records those seqs, and a time-based judgement (c, or the ordering rule) that would rest on such an event fails instead of passing. The test enforces this rule, so a guide cannot name a state that a real run could show differently. (Real runs at scale 1 jitter by milliseconds; 0.25 s is wide. The Dispatcher run at scale 0.5 keeps 125 ms of real margin.) |
| P-7 | **Story mode** (Learn tab, a new `StoryPanel`), shown when the page's demo has a guide and anchors (the 7 Basics now). One chapter per guide step, in order: its number and title, the step text (marked as explanation: a "From the guide" label and the explanation style, S-6), and its state line. **Later chapters are hidden until the one before is revealed** ("3 more chapters"). Chapter states are read from the events the page holds: the live list or the stored history, or the frozen replay when that reaches further (so pausing after a Reveal never makes a moment "disappear"). The anchor's coroutine is found by its `CoroutineCreated`; its events are counted from there (trimming drops the oldest first, so when the creation is held every later event of it is too). States: **ready** (Reveal enabled); **waiting** ("Waiting for this moment", Reveal disabled) — not found and the stream is on; **not held** ("This page's events stop before this moment. Resume the view to follow the run.") — not found and the view is paused; **missed** ("This moment did not happen in this run") — not found although the held events already contain the end of the run (every coroutine created in them has its terminal event), a fact read from the held events themselves, never from a snapshot of another time; **trimmed** ("This moment's events were trimmed, so it can't be shown") — the coroutine is in the session (its snapshot) but its creation is not held, and the server says its history was trimmed (`trimmed`/`oldestRetainedSeq`, now in the frontend type) or the live list hit its 10,000 cap; **incomplete** ("Some of this run's events did not reach this page, so this moment can't be found. Reload the page to read the full history.") — the anchor counts `CoroutineSuspended`/`CoroutineResumed`, which the stream may shed under load (`StructuralClassifier.kt:39`), and the stream reports shed events (`droppedCount > 0`; a reload replays the history unsampled). The other six lifecycle events are never shed. For unavailable states (not held, missed, trimmed, incomplete) a **Skip** link shows the next chapter, so one lost moment never blocks the rest. A chapter without an anchor is revealed with Next (no time move). Revealed chapters stay revealed, with the facts read at Reveal. |
| P-8 | **Reveal moves the page's one moment (S-2, S-11).** Reveal = enter replay at the anchor event (or seek there when already replaying and the frozen events hold it; otherwise re-freeze the newest events and seek). `enterReplay(snapshot?, atSeq?)` gains an optional target seq for its post-entry seek (today always the end). Reveal also selects the anchor's coroutine (one selection), without switching tabs, and makes the whole tree at that moment visible: the state filter goes back to All and completed coroutines are shown (otherwise a completed anchor or expected state would sit in the hidden "completed" group). The Inspector shows it at that moment; the dock stays on Learn. **Reveal is disabled while a recording is armed or running** ("Recording…"): seeking would stall the recorder and re-freezing would move its end. |
| P-9 | **After Reveal** the chapter shows what was recorded at its moment: "At 2.5 s · fetch-product completed" and, per expected state, "fetch-price · Suspended ✓", read from the tree **at the anchor** (`projectCoroutines` of the events up to it, computed in the panel, so it stays right while the user replays elsewhere). A state the tree does not show reads "expected Suspended · the tree shows Active" (honest, never hidden). These lines are recorded facts, styled as such, not as explanation. A "Show this moment again" link re-seeks. |
| P-10 | **Predictions.** A chapter with a prediction shows its question and its 2–3 answers as a radio group before Reveal; choosing is optional and can change until Reveal. Reveal shows the right answer ("Right" / "Not quite: <right answer>"; with no choice, just the answer). |
| P-11 | **Moving on by itself is off by default.** A switch "Show chapters as the run reaches them" (off). When on, the next hidden chapter is revealed automatically once its moment has arrived in the events the page holds, **without moving the time position** (following the run, not jumping); a chapter with an unanswered prediction waits for its answer. Not remembered (each visit starts off). |
| P-12 | **Story state is per page visit.** Revealed chapters and answers live in the panel's state (the dock keeps panels mounted when tabs change, so switching tabs keeps them). A reload starts the story again. |
| P-13 | **What opens first (S-5)** is already right on main: a demo opened with its scenario and not finished opens Tree + Learn. Run again opens the new session the same way. No change. |
| P-14 | **Four looks.** Same markup in every look, new hooks: `story`, `story-chapter`, `story-explanation`, `story-recorded`, `story-prediction`, `story-reveal`, `run-again`. Classic is styled with Tailwind like today's Learn tab and header buttons. A, B and C style the hooks in their own `tokens.css`, appended in a "Part 9" block keyed like the existing rules (a test like `moment-parts.test.ts` checks each look styles each hook). The Run button keeps Classic's look; Run again is a HeroUI primary flat button there. No Classic pixel changes elsewhere. |
| P-15 | **Shared view:** the story works (it only reads events and replays); Run again is not offered. |

## Tests first

Backend (JUnit): `SessionDemoIdTest` cases above; `StoryAnchorsTest` parameterised per demo, plus self-tests of the
P-6 rule on a hand-made event list (a state changing 0.1 s after the anchor is rejected; a descendant's terminal state
at a terminal anchor is accepted). Run the anchor test 5 times in a row (`--rerun`), it must pass every time.

Frontend (vitest), the spec's list: predict, reveal, "waiting for this moment", hidden chapters; Run again leaves the
old session untouched. Plus: trimmed, missed, not held and incomplete states, and Skip; reveal enters replay at the anchor's index, selects its
coroutine, clears the state filter and shows completed coroutines; Reveal disabled while recording; reveal while replaying seeks without re-freezing when the frozen events hold the anchor; the switch reveals
without moving the cursor and stops at an unanswered prediction; expected states read from the tree at the anchor,
including a mismatch; story absent for a demo without anchors; every look styles the new hooks.

## Browser check (ports 18901 / 13901)

Gallery → a Basics demo → Tree + Learn with chapter 1; Run Scenario; chapter 1 waits live, then Reveal: the tree,
Inspector (switch tab) and slider are at the anchor; expected states match the tree; a prediction; later chapters
appear one by one. Run again from a finished demo: a new session opens and runs; the old one is still in the list
with its events. Screenshots in all four looks, dark and light.

## Risks

- **Real-run races** (P-6) — the rule is checked by the test, not by hand.
- **Parts 7 and 10 edit the same files.** New logic sits in new files; `SessionWorkspace`, `SessionHeader` and
  `LearnPanel` get wiring lines only; tokens.css additions are an appended block.
- **Run again leaves an extra session per click.** That is the point (the old one is kept); sessions are deleted
  from the list as before.

- **Plan review round 2 (Codex):** 3 P2, all taken. `VirtualDemoRun` now stamps each event as the session stores it
  (a store wrapper, under the send lock, on the sending thread), so time and thread belong to that event, not to
  whichever callback saw it first. A frozen replay keeps the shed count of the events it froze

  this moment again" is disabled while recording, and the shared reveal handler refuses to seek then. No third plan
  round: the remaining work is building and the code review rounds.
