**Not in this PR:** the Timeline, Problems and Story screens of B (later parts); any change to data, requests, behaviour or the graph's state colours; any Classic pixel.

**Gates** (from `frontend/`): `pnpm exec tsc --noEmit && pnpm lint && pnpm test && pnpm build`.

## 2. The sentence under the title (`HeaderSummary` slot)

**Shared change (minimal):** `looks/types.ts` gets a second slot, `HeaderSummary: (props: HeaderSummaryProps) => ReactNode`; `classic/index.ts` gives Classic `HeaderSummary: () => null` (so Classic's DOM is unchanged); `SessionHeader` calls `useLookSlot('HeaderSummary')` and renders the result right after the `<h1>` (inside the title row), passing only facts it already has: `outcome`, `runSpanNanos`, `spanIsFloor` (`droppedCount > 0`), `replayActive`, `replayAtNanos` and `panelEvents`. A slot here, not CSS, because the sentence is content (plan L0 §5: "B's sentence under the title … via a slot's props"). It is this screen's optional supporting sentence; the later B screens put their status pills beside the title, and they decide their own placement and props when they are built.

**B's `CalmSummary`** (in `b-calm/`), a component returned by the slot (a leaf, so swapping looks remounts nothing that holds state). It words what the page already knows, and says less where it knows less. A pure function `summarise(facts)` builds the words; the component only memoises `projectWaits(events)` and `resourceNames(events)` (pure projections over events the header already holds: no request, no new hook on shared data).

First sentence, by the run outcome (a demo; an attached app has no outcome, so this part is left out):

| Case | Sentence |
|---|---|
| replay | `Replay at 2.3 s.` (the replay cursor; `Replay.` without one). The live outcome is not used: it would contradict the view. |
| not run yet | `Not run yet.` |
| running, span > 0 | `Running for at least 6.0 s.` — the span from the first to the last event is a floor while it runs (the header's own pill shows no length until the run ends, for this reason) |
| running, no span | `Running.` |
| finished | `Finished. Its recorded events span 600 ms.` (`span at least …` when events were dropped; `Finished.` with no span). Once ended, the span is of the events the page holds (a bounded store may have trimmed the first), so it is not called the run's length |
| failed, ended | `1 coroutine failed. The run has ended; its recorded events span 3.0 s.` (`… The run has ended.` with no span) |
| failed, still going | `2 coroutines failed, and the run is still going.` |

Second sentence, the waits the lock, permit and channel wrappers recorded (`projectWaits`, the same source as the cards' "waits for inventory-lock · 1st"), grouped by what they wait for, largest group first, at most three groups and the rest as "N for other things":

- `3 coroutines are waiting: 2 for inventory-lock, 1 for a payment-gateway permit.`
- `1 coroutine is waiting for inventory-lock.`
- channels: `to send to orders`, `to receive from orders`.
- A resource with no name in the events reads `a lock`, `a permit`, `to send`, `to receive` — never its internal id. Two unnamed locks are one group ("2 for a lock").
- No recorded waits: no second sentence. A suspension without a wrapper (a `delay`, an older producer) is never claimed as a wait.

- A run that has ended (live view) gets no second sentence: it waits for nothing, and a wait left by a lost resume is not repeated.

The waits are worded in the present tense, as the cards' second lines are ("waits for inventory-lock · 1st"): the same projection over the same events, so the sentence and the tree never disagree. Nothing at all (no sentence, no element) for an attached app with no waits. The words say "coroutines", not the sketch's "orders": the page does not know what a coroutine stands for.

Not a live region: the header's outcome pill already announces the outcome, and a sentence that changes with every event would be noise for a screen reader.

## 3. Gaps between the sketch and the real page

**The page has, the sketch does not show** (kept, styled calmly):

- the rung badge, the outcome pill, the view pill ("Updating"), the "N coroutines · M events" counts, Reconnect, dropped and new-events chips: they stay on the title line, after the title;
- Run (demos), Export: they stay with the actions;
- the main view's heading ("What's running now"), Show completed, Maximise and the graph's zoom controls;
- the dock's resize handle and Fold button;
- the graph's own frame (its viewport, zoom buttons and full-screen view) — softened, not removed (see §3);
- the graph cards' ID, Job and Scope rows (the sketch's cards show a name, a state pill and the activity line only). Hiding them would hide data the Classic look shows, so they stay; noted for the trial.

**The sketch has, the page does not** (not built):

- "Tree / Timeline" → the page's switch is "Graph / List" (Timeline is a later part);
- a parent card "checkout · waiting for its 7 orders" with a connector: the graph draws its own tree layout and colours (shared, JS), not changed;
- node cards in the sketch's style (white, neutral border, state pill): the cards and their state colours are the graph's, shared;
- "Problems" as the first dock tab: arrives with Part 7;
- the Inspector's two-column "order-5 is waiting for the stock lock" story: the Inspector's content is shared; a later part.
- "Running for 6.0 s": we say "at least", because the page only knows the span of the events it holds.
